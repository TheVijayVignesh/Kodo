# Module 3: Server-Side Web Technology Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a complete, navigable eight-lecture server-side programming module to Kōdo, based on the supplied Web Technology decks.

**Architecture:** Keep Kōdo's data-driven curriculum architecture. Extend types, curriculum registration, progress, and routes; author one typed file per lecture; connect the module to the existing home/navigation/progress UI. Browser exercises will model server concepts without claiming to execute a Node server or database.

**Tech Stack:** Next.js 16 App Router, React 19, TypeScript, Zustand persistence, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-05-module-3-design.md`

## Global Constraints

- Create eight sequential lectures, one corresponding to each supplied deck, arranged for prerequisite flow.
- Teach modern Node.js conventions: `node:` built-in specifiers, Promise-based `fs`, WHATWG URL APIs, and async/await.
- Teach the current MongoDB Node.js driver API rather than the removed callback patterns shown in the slides. Briefly identify legacy snippets where that helps students interpret the supplied notes.
- Teach SQL through placeholders/parameterized queries and distinguish relational SQL concepts from MongoDB documents.
- Correct misleading simplifications in the slides, especially the CAP theorem; do not state that distributed databases simply “choose any two” in all conditions.
- Use the standard local MongoDB URI/port (`mongodb://localhost:27017`) in examples, and use placeholders for credentials rather than literals.
- Add Module 3 without disturbing Module 1/2 content or saved progress.
- Since the browser cannot execute Node.js or connect to a student's local database, server-side examples and exercises must not imply a real Node server or database was run in-browser.

## File map

**Create:**
- `src/lib/curriculum/lectures/m3l01.ts` … `m3l08.ts`: lecture, quiz, and exercise data, one file per lesson.
- `src/lib/curriculum/routes.ts`: one helper for module-aware lecture URLs while preserving the legacy M2 lesson path.
- `src/app/modules/3/[lectureId]/page.tsx`: Module 3 lesson route using the existing lecture view.
- `tests/e2e/module-3.spec.ts`: module listing, lesson route, quiz/exercise, and progress coverage.

**Modify:**
- `src/lib/curriculum/types.ts`: Module 3 IDs, module number, and source kinds.
- `src/lib/store.ts`: persisted progress IDs/default records; retain current storage key/version and M1/M2 records.
- `src/lib/curriculum/progress.ts`: M3 sequence, status, and navigation behavior.
- `src/lib/curriculum/lectures/index.ts`: M3 lecture/quiz/exercise registries and metadata.
- `src/lib/curriculum/sources.ts`: official Node.js, Express, npm, MySQL, and MongoDB sources.
- `src/app/modules/[id]/page.tsx`, `src/components/module/ModuleView.tsx`: M3 module landing view.
- `src/components/home/HomeView.tsx`, `src/components/nav/SiteNav.tsx`, `src/components/nav/SearchPalette.tsx`: M3 links, totals, progress, learning path, and search.
- `playwright.config.ts`: respect an optional `PORT` environment variable so the test web server can use a free port in an environment where port 3000 is occupied.

Do not refactor the overall curriculum architecture or introduce a server runtime, database dependency, or backend to Kōdo. Reuse generic section renderers unless a specific rendering limitation is found.
